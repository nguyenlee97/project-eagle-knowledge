# Cross-review evidence: engine anchor and water

Audit scope: read-only review of the gameplay-lab executable/configuration and default water data for the proposed Teyvat footprint. No game launch or runtime writes were performed.

## Q1 — engine/global anchor

**Finding:** the proposed footprint `X=[-21,465,-4,057], Y=[-7,837,13,667]` lies inside the configured 48 km square engine map `[-24,000,+24,000]` on each horizontal axis. This is a configuration and coordinate-envelope result, not proof that all game subsystems or assets work throughout that footprint.

The lab’s `fastman92limitAdjuster.log` records startup at **2026-10-22 18:48:11 UTC** and identifies **GTA SA 1.0 US HOODLUM**. At that startup, FLA 7.7 logged the 48,000 × 48,000 setting as applied for RenderWare, radar, water, world, and paths (`fastman92limitAdjuster.log:1-12,71-112`). It reports:

- World sectors: `960 × 960 = 921,600`, each `50 × 50 m`.
- LOD sectors: `240 × 240 = 57,600`, each `200 × 200 m`.
- Repeat sectors for vehicles/peds/objects: **`16 × 16 = 256`**. This is a wrapping spatial hash, not a 16×16 cap on world coverage: the reverse-engineered `GetRepeatSector` indexes the repeat list by `abs(sectorIndex) % 16`. With 50 m world sectors, the same bucket repeats every **800 m per axis**. Entity range queries scan the world-sector rectangle, use the corresponding repeat bucket, then filter candidates by entity position/radius and scan codes. Implication: dynamic entities can exist across the expanded map, but distant positions alias to shared buckets and increase candidate-list work; do not call this a hard population/map-coverage limit. FLA’s log remains the evidence that the lab expands the ordinary world-sector table to 960×960.
- Path tiles: **`64 × 64 = 4,096`**, equivalent to 750 m per tile if evenly distributed over 48 km.
- Radar tiles: **`96 × 96 = 9,216`**, 500 m per tile.
- Water blocks: **`96 × 96 = 9,216`**, 500 m per block.

`fastman92limitAdjuster_GTASA.ini:182-210` sets path, radar, water, RenderWare, and world map sizes to 48,000, with 50 m world sectors and 200 m LOD sectors. The same file says that changing path and radar map size requires a new file set (`:182-193`). There are 64 `data/Paths/NODES*.DAT` files, but neither the file count nor the FLA startup log proves those nodes cover Teyvat or offer pedestrian/car routes there. The project’s `gta.dat` loads the alternate S&S map IPLs (`data/gta.dat:138-655`); no Teyvat path/radar resource is registered by the master-plan coordinate formulas alone.

The configured `LOD distance = 300.0` and the log’s applied value (`fastman92limitAdjuster_GTASA.ini:582-583`; `fastman92limitAdjuster.log:300`) corroborate that the proposed 256 m near-sector/subtile approach can remain under the global distance threshold, but do not verify custom LOD visibility or culling. Existing cull IPLs are referenced for other S&S maps; Teyvat-specific cull/occlusion behavior still needs asset-level review. The existing 16×16 repeat-sector grid is a separate hard limit worth planning around for crowds and traffic.

**Negative coordinates and precision:** FLA’s log shows the map/path bounds were extended; it does not establish that every coordinate-consuming subsystem supports arbitrary values in this range. Keep IPL placements and any road/path/cull/zone data within tested limits, and test both extreme corners. The anchor arithmetic’s decimal `0.00 mm` alignment is a mathematical target only. If final game coordinates are stored as binary32 floats, spacing at magnitudes between 16,384 and 32,768 is `0.001953125 m` (about 1.95 mm); serialized placements and mesh seams therefore need a post-quantization comparison. Keep calculations in double precision, serialize shared seam coordinates from one canonical transform, then measure the emitted values. The IEEE source establishes the floating-point-format caveat, not the game’s exact serialization path; verify that path in the exporter/asset format before treating the ULP figure as an observed game result.

**Radar caveat:** FLA’s historical changelog says radar zone reveal is still unsupported outside `[-3,000,+3,000]` (`fastman92.com` lines 924-929). Teyvat’s planned X/Y extents lie outside this interval. The 48 km radar map setting and 9,216-tile table must not be described as proof that zone reveal, map labels, blips, or a Teyvat frontend map work there. Custom raster tiles and in-game verification are still needed.

## Q5 — water reach and capacity

`data/water.dat` is the active default water source: `modloader/modloader.log:789` records `Loading default water level "DATA\\water.dat"`. The file hash at audit time was `DFB67715D3A3F3DD5190CDB5D33EEE04F46434A78853055E60B8923402671975`.

Offline parsing of the file’s `processed` section gives **2,025 input polygons: 2,019 quads and 6 triangles**. Their 8,106 corners are not the loader’s vertex allocation: the reverse-engineered loader interns/reuses vertices by integer X, integer Y, and Z. Applying that key to this file yields **6,425 distinct XYZ keys** before any runtime coordinate-bound handling. The coordinate envelope is `X/Y=[-24,000,+24,000]`; Z ranges from `-5` to `1,082.73` across all records. Four broad outer-ocean quads span the map edges, so the proposed full Teyvat X/Y envelope is within present water geometry. These coarse water surfaces are at Z=0 at their corners; this establishes reach beneath the planned region, not a Teyvat shoreline, river/lake layout, boat route, swimming behavior, or acceptable interaction with terrain. The height range includes localized water definitions and should not be mistaken for one continuous surface at those heights.

The lab INI configures `Water triangles=999`, `Water quads=30,100`, `Water quads and triangles list=9,999`, and `Water vertices=15,200` (`fastman92limitAdjuster_GTASA.ini:412-423`). The raw 6/2,019 polygon counts are below their respective triangle/quad caps; the loader-key estimate of 6,425 unique vertices is below the vertex cap. The list cap must **not** be compared directly with the 2,025 input polygons: the reverse-engineered layout stores a single polygon reference directly in each water block and puts multi-polygon block combinations in a separate sequence list with terminators. Its `FillQuadsAndTrianglesList` implementation delegates to the original executable, so this offline audit cannot calculate/confirm the expanded list’s actual occupancy. The FLA startup log confirms all four configured limits were applied (`fastman92limitAdjuster.log:234-240`) and the 48 km water map has 96 blocks per dimension (`:73-88`); it does **not** log record/unique-vertex/list occupancy or prove behavior at Teyvat during play.

**Native water versus visual water:** the native loader reads `data/water.dat` records into the water polygon/vertex structures; water-level queries (`GetWaterLevel`/`GetWaterLevelNoWaves`) return one water level for a queried position and are used by game interactions. A translucent DFF/alpha water mesh can render a surface, but it does not by itself register a water level for swimming, underwater state, or boats. Teyvat currently has no authored native water-level layout in this audit; its only water data is the general gameplay-lab file.

**Raised and multilevel water:** `water.dat` stores per-vertex Z, so an elevated native basin is representable. The available query interface returns one result level for a position; this review found no evidence that two overlapping native planes at the same XY are independently selectable. For an elevated lake such as Z=1.5, author mutually exclusive/split water footprints or replace the underlying ocean polygon in the lake area instead of simply stacking the lake plane on the broad Z=0 ocean plane. Then verify query selection, shore transitions, swimming, and boats in game. This is a design caution from the query/polygon model, not a claim that all elevated water fails.

**Recommendation:** reserve water-data capacity for explicit authored Teyvat coasts and inland waters, and assess water/terrain intersections at final world Z. Polygon and unique-vertex counts have headroom against the configured caps; the combo-list capacity remains unverified offline. Capacity alone does not establish visual or gameplay correctness. Do not move the continent vertically solely to meet the generic Z=0 sea plane; use regional terrain/water elevations and verify swimming/boat queries in game.

## Evidence boundary

- **Configuration present:** all five map dimensions are 48,000; FLA 7.7 log records those limits applied to the GTA SA 1.0 US HOODLUM executable at the dated startup; water limits are configured and logged as applied.
- **Asset present/readable:** default `data/water.dat` spans the proposed XY envelope and its record count sits under configured caps; 64 path-node files are present.
- **Runtime unproven:** Teyvat placements, paths, radar artwork/zone reveal, culling, terrain-water interaction, swimming, boats, and actual gameplay across the western footprint have not been tested in game by this audit.
