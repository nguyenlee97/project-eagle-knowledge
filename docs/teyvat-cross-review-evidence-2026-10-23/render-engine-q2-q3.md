## Q2 — Interpret the two FLA limits separately

The gameplay-lab INI sets `Collision size = 92768` at `fastman92limitAdjuster_GTASA.ini:577` and `LOD distance = 300.0` at `:583`. The latest available FLA log is from a launch on 2026-10-22 (`fastman92limitAdjuster.log:4`); it records the selected INI at `:20` and reports the applied limits at `:287` and `:300`. This verifies application in that recorded run, not a new launch on audit date. Upstream FLA's development INI labels the former “Max size of single collision from .col archive” and separately labels the latter “LOD distance,” reinforcing that these are different engine settings: [FLA development INI](https://github.com/fastman92/fastman92_limit_adjuster/blob/master/fastman92%20limit%20adjuster/Dev%20INI%20files/fastman92limitAdjuster_GTASA_dev.ini#L2266-L2282).

Treat `92,768` as a per-collision-entry byte-size ceiling, not an allowed face count and not a collision archive total. The builder serializes each `COL3` entry and reports `size_bytes = len(col_entry)` (`build_mondstadt_vertical_slice.py:1081-1119`). Its entry size varies with unique vertices (six bytes each, padded; `:1068-1073`), faces (eight bytes each; `:1077-1079`), and FaceGroups (24-byte bounds per group, up to 48 faces per group; `:1050-1066`), plus the header. Thus a universal “3,200 faces per collision” conversion is unsupported: equal face counts can have different vertex deduplication and FaceGroup overhead; use measured serialized bytes for every COL entry and compare each to the configured cap.

Collision coordinate quantization is componentwise, not a spherical radius check. The builder multiplies local X/Y/Z independently by 128, rounds, and clamps each signed 16-bit component to `[-32767,32767]` (`:1018-1030`). That encodes about `±255.992 m` per axis at 1/128 m precision; a point can be outside the intended coordinate bound in one component while its center distance/radius heuristic still looks acceptable. More seriously, the current code silently clamps instead of rejecting and reporting out-of-range geometry, so a successful binary parse does not prove collision coordinates were preserved. The pivot/radius it computes at `:1013-1016` is only metadata and does not replace this per-axis check.

The `LOD distance = 300` value does not mean every model disappears at a universal 300 m center-distance boundary. The generated IDE separately assigns per-model draw distances `295.0` for near models and `1500.0` for LOD models (`:1449-1457`). In GTA:SA reversed renderer code, visibility uses camera LOD multiplier × the model's draw distance, then additionally considers far clip, “big building” scaling, LOD associations/fades, and object bounds; see [Renderer.cpp visibility logic](https://github.com/gta-reversed/gta-reversed/blob/master/source/game_sa/Renderer.cpp). Its streaming path also computes a per-entity radius and accounts for the associated LOD entity [in Streaming.cpp](https://github.com/gta-reversed/gta-reversed/blob/master/source/game_sa/Streaming.cpp). Consequently the builder comment at `:1449` (“295 < 300 so full COL3 physics”) is not established by these numbers or sources: IDE draw distance and COL ownership/loading are distinct mechanisms. The reversed code shows COL files loaded through `CColStore` and model collision binding in [FileLoader.cpp](https://github.com/gta-reversed/gta-reversed/blob/master/source/game_sa/FileLoader.cpp); it does not show a generic `<300` switch that guarantees collision for a particular entity. The particular lab configuration has not been experimentally tested at tile boundaries.

Practical follow-up for the builder: validate each actual entry's encoded local X, Y, and Z extrema before packing and fail on any overflow; validate each exact serialized entry size against `92,768`; keep IDE near/LOD distances as visibility tuning; separately prove collision availability/continuity in game or through a representative engine test. Face count can remain a secondary performance metric, but is not the cap itself.

## Q3 — What the DFF and SkyGfx settings mean

The builder's DFF geometry struct sets `0x0001007E`, explicitly including `PRELIT`, `TEXTURED`, and `MODULATEMATERIALCOLOR` (`build_mondstadt_vertical_slice.py:854-884`). It packs the computed daytime RGBA array as standard prelight data (`:883-891`), writes the night RGBA values into custom ExtraVertColour extension `0x0253F2F9` (`:958-966`), and creates white RGBA textured materials (`:923-942`). RenderWare's flag definitions confirm `PRELIT = 0x08` and `MODULATEMATERIALCOLOR = 0x40`: [DragonFF DFF constants](https://github.com/Parik27/DragonFF/blob/master/gtaLib/dff.py#L2258-L2274).

That is structurally compatible with GTA:SA's day/night custom building pipeline. The reversed source registers the ExtraVertColour plugin (`CCustomBuildingDNPipeline.cpp:816-857`), reads its payload as a magic value followed by per-vertex night RGBA and copies the ordinary DFF prelight array into the day array (`:911-932`), then interpolates day/night into the active prelight colors as the day/night balance changes (`:980-999`). This supports the intended textured mesh × vertex-prelight pattern. It does not prove that Project Eagle's exact `skygfx.asi` build attaches this pipeline to these models, or that those assets render correctly in the lab. The DFF has two color sets in the practical sense of ordinary prelight plus ExtraVertColour; the extended SkyGfx config also documents automatic building-pipeline attachment for models with two vertex-color sets (`skygfx1.ini:98-105`), but that behavior has not been observed in game.

The existing `skygfx1.ini` is a materially mixed preset: `buildingPipe=PS2` (`:27`), `ps2Modulate=0` and `dualPass=1` (`:23-24`), `detailMaps=1` (`:30`), `doRadiosity=1` (`:67`), and `disableGamma=1` (`:76`). `ps2ModulateBuilding=1` is commented out while `ps2ModulateGrass=1` is active (`:105-106`). Upstream SkyGfx reads building modulation from `ps2ModulateBuilding`, falling back to the global `ps2Modulate` value (`main.cpp:3754-3782`), so this file's effective building-modulate setting is 0 while grass is 1. That SkyGfx-specific option is separate from the standard RenderWare `MODULATEMATERIALCOLOR` geometry flag: do not infer from `ps2Modulate=0` that DFF prelight × texture modulation is absent. SkyGfx source explains the building and modulation settings and their fallback [in its config reader](https://github.com/aap/skygfx/blob/master/src/main.cpp#L3754-L3782); the repository describes it as a graphics pipeline recreation, not a DFF conformance test [in its README](https://github.com/aap/skygfx/blob/master/readme.md#L188-L190).

There is no `skygfx.ini` in the lab root, while `skygfx1.ini` and `skygfx.asi` are present. Upstream source scans numbered `skygfx1..9.ini` presets and reads the numbered file into a preset slot (`main.cpp:3607-3748`); the local file therefore is a discoverable preset. The available Mod Loader log contains no `SkyGfx` line, and no current run-time preset/status record was found. So report these as the available on-disk preset values, not as independently verified active runtime values.

Two texture/color cautions follow from the code. First, `compute_vertex_prelight` does not bake the sampled source RGB into daytime prelight: daytime is driven by normal, height, and AO and clamps RGB to at least 145 (`:758-795`). The sampled RGB only classifies warm windows for night colors (`:783-794`). Therefore this city writer is not evidence that the master plan's `BaseMap → geographic vertex-color` terrain bake has been implemented. Second, its LOD passes neutral `(190,190,190)` for every sample when generating night prelight (`:1367-1382`), and the LOD compiler receives no 2dfx lights (`:1388-1399`); the near and LOD night appearance can therefore diverge, especially for warm windows. For terrain diagnosis, start with grayscale/near-white tiled albedo and neutral output settings, establish that vertex-color geographic blocks read correctly, then add colored detail. Otherwise colored texture albedo multiplied by geographic vertex color and day/night prelight makes a color shift hard to attribute. Also avoid applying a single horizontal planar UV mapping to steep cliff faces: it changes texture density with slope and can smear/stretch cliffs; classify/project steep faces separately (or use triplanar mapping). Neither the exact planned terrain shaders nor any resulting in-game transition has been validated by this audit.

## Independent byte parse of the current staging COL (ID 6715)

I independently walked every `COL3` entry in `D:\GTA Archive\Staging\mondstadt-vertical-slice-2026-10-23\models\col\mondstadt_city.col` using the COL3 header/offset layout emitted by the builder and cross-checked the entry size against the archive boundaries. Archive SHA-256: `896D4134201CBA4547153D3B232855D43835FE0275BDBFAF001D0267AADEC5BD`. Entry 6715 is exactly 16,896 bytes and ends cleanly before the next/file boundary. It has 1,257 faces, 993 quantized vertices, and 27 FaceGroups.

Its stored floating bounds say Y = `[-299.678192, +299.677246]` and sphere radius `342.021118 m`; the corresponding compressed vertex component (third value in this builder's `(X, GTA Y, GTA Z)` tuple) reaches only `[-32767,+32767]`, i.e. `[-255.9921875,+255.9921875] m`. Exactly **105 of 2,979 scalar components** equal the clamp endpoints: 51 negative and 54 positive, all in this Y component. The represented ends therefore stop short of the declared bounds by up to `43.686 m`. This confirms actual geometry deformation in the compiled collision entry, rather than a theoretical limit warning. It follows directly from the clamping at builder lines 1022-1029 and the header bounds being computed earlier from unclamped input at lines 1007-1016.

The same binary has an independent identity defect at ID 6713. Its COL header model-name field is `md_city_barbatos_plaz`; the builder spec and IDE/placements use `md_city_barbatos_plaza` (22 ASCII bytes; builder spec line 60, staged IDE line 7 and IPL lines 7/13). The writer explicitly truncates COL names to 21 bytes and null-pads the 22-byte field (`build_mondstadt_vertical_slice.py:1086`), while the DFF writer permits up to 23 bytes (`:878`) and the DFF file/model name is the full name. GTA:SA reversed defines the COL header model-name buffer as 22 bytes ([ColHelpers.h](https://github.com/gta-reversed/gta-reversed/blob/master/source/game_sa/Collision/ColHelpers.h#L733-L783)); the COL first-load path accepts the numeric ID only when its model key matches the header name, then falls back to looking up the header name ([FileLoader.cpp](https://github.com/gta-reversed/gta-reversed/blob/master/source/game_sa/FileLoader.cpp#L3123-L3158)). With the observed truncation, the 6713 key comparison cannot match the full IDE key; unless an object with the truncated alias exists in the loaded model range, the fallback will not bind this collision to 6713. This is a source-backed likely loader failure, not a runtime-observed one. Repair by using a ≤21-byte shared model name across DFF, IDE, IPL and COL (or by another verified loader-compatible alias strategy), then rebuild and inspect the resulting file before considering the slice valid.
